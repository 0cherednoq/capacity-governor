# Выпуск

Публикация идёт через **trusted publishing**: токенов PyPI в секретах репозитория нет,
GitHub Actions получает короткоживущий OIDC-токен на время работы. Поэтому украсть
можно только сам доступ к репозиторию, а не ключ, который живёт до отзыва.

Выпуск запускается тегом и проходит через окружение `pypi`, где стоит обязательное
ревью: случайный тег не публикует пакет.

---

## Что настроить один раз

### 1. Репозиторий

```bash
gh repo create capacity-governor --private --source . --remote origin --push
```

`--private` можно заменить на `--public`, когда решите открывать код. Trusted
publishing работает с обоими.

### 2. Окружения GitHub

Settings → Environments, два окружения:

| Окружение | Зачем | Защита |
|---|---|---|
| `pypi` | публикация выпуска | Required reviewers — вы; Deployment branches — только теги `v*` |
| `testpypi` | прогон публикации | без защиты |

Ревью в `pypi` — не формальность: загруженную версию нельзя заменить, только
удалить (и номер останется занятым навсегда).

### 3. Доверенный издатель на PyPI

На [pypi.org](https://pypi.org/manage/account/publishing/) → Add a new pending
publisher (имя проекта ещё не занято, поэтому publisher заводится заранее):

| Поле | Значение |
|---|---|
| PyPI Project Name | `capacity-governor` |
| Owner | `0cherednoq` |
| Repository name | `capacity-governor` |
| Workflow name | `release.yml` |
| Environment name | `pypi` |

То же на [test.pypi.org](https://test.pypi.org/manage/account/publishing/) с
окружением `testpypi`.

Имя `capacity-governor` на PyPI свободным может не оказаться — проверьте до первого
выпуска: `pip index versions capacity-governor`. Если занято, меняется `name` в
`pyproject.toml`, и publisher заводится под новое имя; импортируемые пакеты
(`capacity`, `capacity_adapters`) при этом не меняются.

---

## Как выпускать

1. Поднять версию в `pyproject.toml` и перенести раздел «Не выпущено» в `CHANGELOG.md`
   под новый заголовок `## vX.Y.Z` — из него берутся заметки релиза.
2. Закоммитить, поставить тег, отправить:

   ```bash
   git commit -am "Release v0.1.0"
   git tag v0.1.0
   git push origin main v0.1.0
   ```

3. Работа `release` проверит код (ruff, mypy, 225 тестов с живым Postgres), сверит тег
   с версией пакета, соберёт sdist и wheel и проверит колесо в чистом окружении.
4. Подтвердить деплой в окружении `pypi`. После публикации создаётся релиз GitHub с
   артефактами и заметками из `CHANGELOG.md`.

### Прогон без последствий

Actions → release → Run workflow → `testpypi`. Пройдёт весь путь, кроме публикации в
настоящий индекс. Полезно перед первым выпуском: ошибку в метаданных на TestPyPI можно
исправить, в PyPI — нет.

---

## Чего в выпуске нет намеренно

**Версия пакета не трогается автоматически.** Никакого bump-бота: `0.1.0` означает,
что API может измениться, и решение о номере — осознанное, а не следствие слов в
сообщении коммита.

**Интеграция с Tallyho и Identity Hub в CI не прогоняется.** Эти пакеты не в публичном
индексе, поэтому их тесты там пропускаются — Postgres поднимается, остальное проверяется
локально. Перед выпуском стоит прогнать всё у себя:

```bash
pytest -q   # 225 тестов, включая 27 интеграционных
```
