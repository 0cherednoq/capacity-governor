# Сценарии

Четыре разбора под разные виды дефицитного ресурса. Код каждого лежит в `examples/` и
запускается без базы и внешних сервисов — состояние живёт в памяти:

```bash
python -m examples.proxy_pool
```

Подбирайте сценарий не по названию ресурса, а по тому, как он расходуется.

| Если ресурс… | Берите | Пример |
|---|---|---|
| делится между несколькими потребителями одновременно | `MaxMinFair` | [прокси](#прокси-между-скраперами), [слоты GPU](#слоты-gpu-между-командами) |
| закреплён за одним потребителем и расходуется по очереди | `Sequential` | [отправители рассылки](#отправители-рассылки) |
| не меняется и делить его нечего | `StaticCeiling` | — |
| кончается и его докупают или заводят заново | `ReorderPoint` | [квота API](#квота-внешнего-api) |

## Прокси между скраперами

**Ресурс:** пул прокси, который делят несколько заданий скрапинга.
**Файл:** [`examples/proxy_pool.py`](../examples/proxy_pool.py)

Задача: раздать 12 прокси трём заданиям так, чтобы срочное получало вдвое больше
остальных, но никого не вытесняло, а освободившаяся доля сразу уходила тем, кто ещё
работает.

```python
registry = MemoryRegistry([
    ConsumerState("urgent-scrape", demand=500, weight=2),
    ConsumerState("daily-scrape", demand=500, weight=1),
    ConsumerState("backfill", demand=500, weight=1),
])
```

Результат прогона:

```
по весам 2:1:1 из 12 прокси → {'urgent-scrape': 6, 'daily-scrape': 3, 'backfill': 3}
срочное закончило, доля ушла остальным → {'urgent-scrape': 0, 'daily-scrape': 6, 'backfill': 6}
осталось 6 прокси → {'urgent-scrape': 0, 'daily-scrape': 3, 'backfill': 3}
```

Что здесь важно понять про веса: это не приоритет в смысле «сначала один, потом
другой». Вес задаёт скорость, с которой заполняется доля потребителя, поэтому при
нехватке ресурса все получают что-то, а не выстраиваются в очередь за первым.

Ровно этот же сценарий работает для браузерных профилей, слотов антидетект-браузера,
воркеров с лицензиями и любого пула, где несколько потребителей берут ресурс
параллельно.

## Слоты GPU между командами

**Ресурс:** слоты инференса на видеокартах.
**Файл:** [`examples/gpu_slots.py`](../examples/gpu_slots.py)

Задача: продовому сервису нельзя опускаться ниже двух слотов; исследовательской
очереди гарантий не нужно; batch-переобучению больше трёх слотов отдавать бессмысленно.

```python
ConsumerState("prod-inference", demand=100, guaranteed=2)   # минимум
ConsumerState("research-queue", demand=100)                 # как получится
ConsumerState("batch-retrain", demand=100, ceiling=3)       # потолок
```

```
8 слотов, гарантия 2 и потолок 3 → {'prod-inference': 4, 'research-queue': 2, 'batch-retrain': 2}
осталось 4 слота → {'prod-inference': 3, 'research-queue': 0, 'batch-retrain': 1}
остался 1 слот, гарантия не создаёт ресурс → {'prod-inference': 1, 'research-queue': 0, 'batch-retrain': 0}
```

Последняя строка — то, о чём стоит помнить, обещая кому-то гарантию: политика выдаёт
её раньше всех остальных, но взять слот неоткуда, если карт физически нет. Гарантия
определяет очерёдность, а не наличие.

## Отправители рассылки

**Ресурс:** почтовые отправители, закреплённые за кампанией.
**Файл:** [`examples/mailing_senders.py`](../examples/mailing_senders.py)

Здесь делёжка противопоказана. Репутация адреса набирается последовательным прогревом,
и чередование отправителей её портит: вместо одного прогретого адреса получается пул
одинаково холодных. Поэтому `Sequential` — окно 1, пока текущий отправитель жив, и 0,
когда он умер.

```
окно 1, отправлено 200 через warm-1
отправитель умер, окно → 0
писем ушло, пока окно закрыто: 0
после переключения окно 1, отправлено 200 через warm-2
после опоздавшего отчёта текущий остался: warm-2
```

Переключение на следующего отправителя библиотека намеренно не делает: оно идёт под
блокировкой строки кампании и сравнивает «текущий == умерший». Без этой проверки
опоздавший отчёт о смерти прежнего отправителя уводит кампанию через весь пул за
несколько секунд — в примере видно, как сравнение это гасит.

Так же устроены SMS-шлюзы с номерами, торговые аккаунты с прогревом лимитов и любой
ресурс, который «разогревается» под одного потребителя.

## Квота внешнего API

**Ресурс:** ключи стороннего API с лимитом вызовов.
**Файл:** [`examples/api_quota.py`](../examples/api_quota.py)

Это вторая половина библиотеки: не «кому сколько сейчас», а «когда пополнять».
`ReorderPoint` отвечает на три вопроса одновременно.

```
обычный день: запаса хватает                запас  18.0 нужно   5.0 в работе  0 → заказать 0
запас просел ниже планки                    запас   4.0 нужно   2.0 в работе  0 → заказать 5
наплыв: планка цела, но работы больше запаса запас  15.0 нужно  40.0 в работе  0 → заказать 5
заявки уже в работе — повторно не заказываем запас   4.0 нужно   2.0 в работе 16 → заказать 0
бюджет суток исчерпан                       запас   0.0 нужно  10.0 в работе  0 → заказать 0
```

Четвёртая строка — главная. Заказы в работе входят в расчёт, поэтому контур не
закажет повторно то, что уже едет: без этого он на каждом такте дозаказывал бы одно и
то же, пока идёт предыдущая партия.

Ключ заказа привязан к началу бюджетного окна, а не к моменту такта:

```
ключ заказа в 09:30 → replenish:2026-03-14T00:00:00+00:00
ключ заказа в 23:59 → replenish:2026-03-14T00:00:00+00:00
ключ заказа назавтра → replenish:2026-03-15T00:00:00+00:00
```

Так повторный такт в тех же сутках дописывает недостающие заявки вместо новой пачки.
Если считать бюджет по одному окну, а дедуплицировать заказы по другому, лимит
перестаёт работать — заявки будут уходить дважды.

Подходит для всего, что кончается и восполняется: аккаунты, которые регистрируют,
номера, прокси с оплатой за трафик, предоплаченные кредиты любого сервиса.

## Как собрать это в рабочий контур

Примеры выше показывают политику. Чтобы она применялась сама, её оборачивают в
контур — он раз в несколько секунд читает ёмкость и спрос, считает окна и пишет
только изменившиеся. Сборка и порядок такта описаны в
[`docs/architecture.md`](architecture.md), оператор управляет контуром командами
`pin`, `unpin`, `pause`, `resume`.
