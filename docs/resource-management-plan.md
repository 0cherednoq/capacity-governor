# capacity-governor — план реализации

Источник требований: `talyho/docs/resource-management.md` §7, §8, §12, §15.
Это новая библиотека: кода нет, проверять было нечего. Поэтому здесь не вердикты, а
разбор обоснованности и конструкция.

---

## G0. Нужна ли отдельная библиотека

### Обоснование документа — принимается, с условием

Аргументы §3 документа верны:

* дефицитным бывает не только аккаунт: прокси (подтверждено — `LeaseUnavailableReason.NO_PROXY`
  существует в Identity Hub), браузеры, слоты GPU. Значит политика не может жить в
  Identity Hub;
* Tallyho — учёт работы; положив в него политику раздачи ёмкости, мы разменяем его
  главное свойство на удобство одного сценария;
* политика как чистая функция тестируется таблицами и прогоняется в симуляции без БД.

Но «отдельная библиотека» и «отдельный пакет на PyPI с CI, extras и релизным циклом» —
разные решения. Ядро политик — это порядка 200–300 строк чистых функций. Заводить под
них третий публикуемый пакет до того, как появился второй потребитель, — это
преждевременная граница.

### Решение: гейт на вынос

| Фаза | Где живёт | Условие перехода |
|---|---|---|
| **A** | модуль `capacity/` **внутри проекта** domain-checker: те же типы, те же чистые политики, тот же контур | после Tallyho T1–T4 и Identity Hub I1 |
| **B** | отдельный пакет `capacity-governor` с extras `[tallyho]`, `[identity-hub]` | когда политики заработали на **двух** сценариях: проверка доменов (`MaxMinFair`) и рассылка (`Sequential`) |

Это ровно то, что говорит §15 документа («после пунктов 1–5 … с распределителем в коде
проекта. Пункты 6–8 переносят распределитель в библиотеку») — здесь это закреплено как
условие, а не как последовательность по времени. Код фазы A пишется сразу в виде,
который переносится копированием: чистое ядро без импортов проекта, адаптеры отдельным
модулем.

## G1. Ядро: порты

Порты §12.2 документа принимаются почти без изменений. Три правки:

**1. Типы ёмкости рассогласованы.** `CapacitySource.capacity() -> int`, а
`SupplySnapshot.effective_available: float`. «Эффективные аккаунты» (сумма кредитов,
делённая на кредиты нового аккаунта) — величина дробная, а окно — целое. Нужно явно:
ёмкость для раздачи — `int` (floor от эффективной), ёмкость для пополнения — `float`.
Пограничный случай: 0.9 эффективного аккаунта даёт `capacity = 0`, то есть окна 0 и
работа встаёт, хотя кредиты есть. Поэтому floor применяется к `allocatable`, и у
политики есть `min_grant_floor: int = 0` — сколько выдать потребителю при ёмкости
между 0 и 1, если нужно дать работе шанс доесть остаток (по умолчанию 0: лучше встать,
чем жечь попытки).

**2. `ConsumerState.max` затеняет встроенный `max`.** Переименовать в `ceiling`
(ruff A003 это и поймает).

**3. `CapacitySource` отдаёт не число, а структуру.** Контуру нужны для наблюдаемости
`eligible`, `free`, `leased`, `reserved` (всё это даёт `EligibleCapacity` из
`AccountLibrarry/docs/resource-management-plan.md`), а политике — только `allocatable`. Порт возвращает структуру,
политика получает `int`.

```python
@dataclass(frozen=True, slots=True)
class ConsumerState:
    consumer_id: str
    demand: int
    weight: int = 1
    guaranteed: int = 0
    ceiling: int | None = None

@dataclass(frozen=True, slots=True)
class Allocation:
    grants: Mapping[str, int]
    deficits: Mapping[str, int]      # переносится в следующий такт

class AllocationPolicy(Protocol):
    def allocate(
        self, capacity: int, consumers: Sequence[ConsumerState],
        deficits: Mapping[str, int],
    ) -> Allocation: ...
```

Политика остаётся чистой: ни БД, ни времени, ни `tick` как счётчика — вместо номера
такта передаются `deficits`, то есть явное состояние (см. G2).

## G2. `MaxMinFair` — исправление: deficit round robin вместо `rotate=True`

### Что предлагает документ и в чём пробел

§7.1: раздача по одному по кругу, «порядок обхода сдвигается каждый такт», при ёмкости
2 на трёх потребителей выдача идёт `1/1/0`, затем `0/1/1`. Идея верная, реализация
через сдвиг по номеру такта — хрупкая: при появлении и исчезновении потребителей
между тактами (а батчи создаются и финализируются постоянно) сдвиг по индексу
перестаёт соответствовать тому, кто уже получал, и потребитель может пропускать круги
систематически.

Стандартное решение этой же задачи — **deficit round robin**: у каждого потребителя
счётчик недополученного, он пополняется на `weight` каждый такт и тратится при выдаче,
остаток переносится. Потребитель, которому не досталось, в следующий такт стоит первым
по построению, а не по номеру такта. В Kueue та же мысль выражена как «очерёдность по
историческому потреблению» (Admission Fair Sharing).

### Алгоритм

Прогрессивное заполнение (progressive filling) — канонический способ считать max-min
fair; весовой вариант = скорости заполнения пропорциональны весам; гарантированный
минимум = начинаем с него; потолок = виртуальное ограничение спроса.

```
1. headroom(c) = min(c.demand, c.ceiling or ∞)
2. Гарантии: по порядку убывания deficit выдать min(c.guaranteed, headroom(c), remaining)
3. Заполнение: пока remaining > 0 и есть c с grant < headroom(c):
     W = Σ weight активных
     если remaining >= W:
         level = remaining // W
         каждому активному выдать min(level * weight, headroom - grant)
     иначе:
         # единиц меньше, чем весов: раздать по одной в порядке убывания deficit
         remaining штук активным, отсортированным по (-deficit, consumer_id)
         break
     пересчитать активных
4. deficits' = {c: deficit + weight - (grant - guaranteed_part)}, снизу ограничено 0,
   сверху — deficit_cap (иначе давно спавший потребитель получит всё и вытеснит остальных)
5. Потребитель, которого нет в этом такте, свой deficit теряет (ключ удаляется)
```

Шаг 4 с `deficit_cap` обязателен: без него потребитель, простоявший сутки с нулевым
спросом, вернётся с огромным кредитом. Ограничение — несколько тактов, например
`deficit_cap = 4 × weight`.

### Таблицы приёмки

Таблица §7.1 документа переносится в тест как есть:

| Ёмкость | Спрос A / B / C | Ожидаемая выдача |
|---|---|---|
| 30 | 1000 / 5 / — | 25 / 5 / — |
| 30 | много / много / много | 10 / 10 / 10 |
| 6 | много / много / много | 2 / 2 / 2 |
| 2 | много / много / много | 1 / 1 / 0, затем 0 / 1 / 1, затем 1 / 0 / 1 |
| 0 | много / много / много | 0 / 0 / 0 |

Плюс случаи, которых в документе нет и которые обязаны быть в таблице:

| Случай | Ожидание |
|---|---|
| `weight` A=2, B=1, ёмкость 3, спрос у обоих большой | 2 / 1 |
| `guaranteed` A=5, ёмкость 4 | A получает 4, B — 0 (гарантия не создаёт ёмкость) |
| `ceiling` A=3, ёмкость 100, спрос A огромный, B нет | A получает 3, 97 не раздаётся |
| спрос 0 у всех, ёмкость 50 | 0 / 0 / 0 (не выдаём окно под отсутствующую работу) |
| 100 потребителей, ёмкость 1 | за 100 тактов каждый получил ровно один раз |
| потребитель исчез и вернулся через 1000 тактов | его выдача не больше `deficit_cap` сверх доли |

## G3. `Sequential` — уточнение границ

§7.2 документа технически корректен и его главная мысль — **правильная и
неочевидная**: аренда должна идти строго по текущему ресурсу (`among=[current]`),
иначе Identity Hub, выбирая давно не использованный аккаунт, начнёт их чередовать и
последовательный расход превратится в размазывание по всему пулу.

Два уточнения:

* переключение под блокировкой строки потребителя со сравнением «текущий == умерший» —
  обязательно, и это **не политика, а домен**. В библиотеке остаётся только функция
  `Sequential.allocate` (1 при живом ресурсе, иначе 0), а переключение
  `Campaign.current_sender_id` пишет проект. Поэтому `Sequential` в контуре
  практически не нужен: окно выводится из статуса кампании в транзакции смены статуса
  (§9.2 документа) — через `handle.set_max_in_flight(limit, session=…)`;
* следствие: в фазе A `Sequential` вообще не требует контура. Это аргумент за то,
  что гейт G0 проходится только после того, как рассылка поработает.

## G4. `ReorderPoint` — (s, S) + нехватка + бюджет

### Правила §8.1 — принимаются

Три правила документа (планка `(s,S)`, нехватка под спрос, бюджет) — это стандартная
политика запасов плюс два ограничителя, и примеры §8.2 согласованы. Учёт «заказов в
работе» — обязателен, документ это верно подчёркивает.

```python
@dataclass(frozen=True, slots=True)
class SupplySnapshot:
    effective_available: float
    needed_for_demand: float
    ordered_in_progress: int
    ordered_in_window: int

def to_order(self, supply) -> int:
    position = supply.effective_available + supply.ordered_in_progress
    by_level = ceil(self.target - position) if position < self.reorder_ratio * self.target else 0
    by_shortfall = max(0, ceil(supply.needed_for_demand - position))
    want = max(by_level, by_shortfall)
    return max(0, min(want, self.max_per_window - supply.ordered_in_window))
```

`position` (инвентарная позиция = запас + заказанное) считается один раз и входит в
оба правила — иначе второе правило закажет повторно то, что уже заказано первым.

### Кто ведёт бюджетный журнал — пробел в портах

`SupplySnapshot.ordered_in_window` обязан откуда-то взяться, а в портах §12.2 нет
ничего, что его хранит: политика чистая, `Replenisher` только заказывает. Ответ:
`SupplySource` реализует **проект** (так и указано в примере §12.4), и у проекта есть
своя таблица регистраций. Политика хранилища не получает.

Для случая «журнал — это сами батчи Tallyho» нужен готовый адаптер:
`TallyhoOrderLedger` поверх `th.list_batches(kinds=[…], created_after=now-window)` +
`view()` по найденным батчам. Батчей за окно единицы, цена чтения — единицы запросов,
не на каждый такт (кэш на длительность такта).

### Идемпотентность заказа — работает как описано

Схема §8.3 (батч с `key` по минуте, items с `opts(key=f"slot:{i}")`) опирается на
существующий в Tallyho уникальный индекс `(batch_id, key) WHERE key IS NOT NULL`
(§5.2 ARCHITECTURE). Повторный такт в том же окне допишет только недостающие слоты.
Это корректно и не требует доработок Tallyho.

Пограничный случай, которого нет в документе: окно бюджета, выраженное минутой ключа,
и окно бюджета политики (`window=1h`) — разные вещи. Ключ батча должен быть
`replenish:{window_start}`, где `window_start` — начало **бюджетного** окна, иначе
`max_per_window` будет считаться по одному окну, а дедуплицироваться по другому.

## G5. Мёртвая зона и стабилизация — главное, чего нет в документе

Документ вводит гистерезис только для пополнения (`(s,S)`) и прямо называет его в
словаре. Но у **контура раздачи** гистерезиса нет: §12.4 пересчитывает окна каждые 5
секунд и выставляет их абсолютно. Между тактами ёмкость меняется непрерывно — баланс
тает с каждой проверкой домена. Значит окна будут дёргаться каждые 5 секунд, а каждое
уменьшение окна — это парковка записей outbox, каждое увеличение — распарковка, то
есть запись в БД на пустом месте.

Ровно эту задачу решает HPA в Kubernetes, и его решение проверено масштабом:

| Механизм HPA | Значение | Аналог здесь |
|---|---|---|
| мёртвая зона (tolerance) | ±10 %: при отношении 0.9…1.1 не делать ничего | `apply` не трогает окно, если \|new − cur\| < max(1, 0.1 × cur) |
| окно стабилизации вниз | 300 с: берётся самая консервативная рекомендация из окна | при **уменьшении** окна берём максимум рекомендаций за `stabilize_down` |
| окно стабилизации вверх | 0 с: вверх реагируем сразу | увеличение применяем сразу |
| такт | 15 с | 5 с (ресурс дороже, задержка важнее) |

Асимметрия намеренная: вверх — сразу (работа стоит, это дорого), вниз — медленно
(ёмкость могла мигнуть). Исключения из мёртвой зоны, применяются всегда:

* `new == 0` — ресурс кончился, останавливаем немедленно;
* `cur == 0` и `new > 0` — ресурс появился, запускаем немедленно;
* потребитель появился или исчез.

Без этого пункта контур будет работать, но создаст постоянный фон записи в БД и
дрожание в админке. С ним достаточно `every=5s` без всякой событийной подписки — что
ещё раз понижает приоритет I2 в Identity Hub.

## G6. Контур: лидер, такт, применение

### Лидер — транзакционный advisory lock, не сессионный

§12.4 говорит «лидер выбирается advisory lock в Postgres, по образцу maintenance
Tallyho». Образец надо брать точно: Tallyho использует `pg_try_advisory_xact_lock`
(§11.2 ARCHITECTURE). Разница принципиальна:

* **сессионный** `pg_try_advisory_lock` держится за соединением. Под PgBouncer в
  режиме transaction/statement pooling соединение между запросами возвращается в пул,
  и такой лок либо теряется, либо удерживается не тем, кто думает. Библиотеки
  лидер-элекшена на advisory locks прямо требуют отключать мультиплексирование и
  пинить соединение к primary;
* **транзакционный** `pg_try_advisory_xact_lock` живёт внутри транзакции и снимается
  коммитом — безопасен под любым пулером.

Решение: лок берётся **на каждый такт** внутри транзакции такта. Не получил — такт
пропущен, следующий через `every`. Лидерства как состояния нет, значит нет и
расщепления лидера, stale-лидера и healthcheck'а соединения. Цена — такт не может
быть дольше транзакции; он и не должен: чтение ёмкости, чтение спроса, UPDATE окон.

### Применение

* `apply` выставляет **абсолютные** окна через `handle.set_max_in_flight(limit, session=tx)` —
  все окна такта одной транзакцией. Повтор такта ничего не ломает;
* окно, не изменившееся после G5, не пишется вовсе;
* `governor.kick()` — пересчитать сейчас, по событиям Identity Hub (`pool.capacity.ok`,
  `pool.capacity.low`) и проекта. `kick()` дебаунсится: не чаще раза в
  `min_tick_interval`, иначе пополнение на 20 аккаунтов вызовет 20 пересчётов;
* заказ пополнения — после применения окон, в своей транзакции (это постановка работы,
  а не чтение).

### Наблюдаемость

На каждом такте: `capacity.eligible/free/leased/reserved`, суммарный спрос, выдача по
потребителям, дельта окон, число пропущенных по мёртвой зоне, заказ пополнения и
остаток бюджета. Это и есть график загрузки пула для админки. Аналог поля
`status.fairSharing.weightedShare` и метрики `kueue_cluster_queue_weighted_share` в
Kueue — полезно отдавать и нормированную долю, по ней сразу видно перекос.

## G7. Ручное переопределение — обязательно, в документе нет

Автоматический контур, который может поставить всем окно 0, обязан иметь
выключатель, иначе оператор не сможет вмешаться во время инцидента:

* `governor.pin(consumer_id, limit)` / `unpin(consumer_id)` — потребитель исключён из
  раздачи, его окно контур не трогает. Политика получает его как потребителя с
  `ceiling = limit`, чтобы его потребление по-прежнему вычиталось из ёмкости;
* `governor.pause()` — контур перестаёт писать окна вовсе, оставляя текущие значения.
  Для диагностики: «это контур дёргает окна или нет»;
* и `pin`, и `pause` — состояние в БД, не в памяти процесса: лидер меняется между
  тактами.

## G8. Симуляция на SimPy

§12.6 документа — хорошее решение, оно и позволяет принимать параметры (`target`,
`reorder_ratio`, `max_per_window`, `tolerance`, `stabilize_down`) не на глаз. Модель:
аккаунты — `FilterStore`, кредиты — `Container`, браузеры — `Resource`.

Прогоны, которые должны быть в наборе:

1. **холодный старт**: 0 аккаунтов, 100 доменов — проверяем, что правило «нехватка под
   спрос» вытягивает работу, а бюджет её не душит навсегда;
2. **обычные сутки**: убеждаемся, что заказов 0 и окна не дрожат (прямая проверка G5 и
   I1);
3. **наплыв ×10**: работа растягивается на часы по бюджету, но не проваливается;
4. **ёмкость < числа потребителей**: никто не голодает (проверка G2, DRR);
5. **бан половины пула в один момент**: окна уходят в 0, `defer` держит работу,
   пополнение поднимает пул, работа продолжается — это сценарий §13 документа в
   масштабе;
6. **колеблющаяся ёмкость** (аккаунты входят и выходят из COOLING): число записей окон
   за прогон — метрика качества мёртвой зоны.

Симуляция живёт в dev-зависимостях и в CI гоняется с фиксированным seed: политики
чистые, значит прогон детерминирован.
